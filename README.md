# Starfield Handle Parser

`starfield_handle_parser.py` parses Starfield `DumpPointerHandles` logs and
attributes each handle to the plugin that actually owns the FormID prefix.
That matters because the dump's `ModIdx` field is often misleading in large
load orders.

Instead of trusting `ModIdx`, the script resolves ownership from the FormID:

- `00` to `FC` prefixes map to full plugins
- `FDxx` prefixes map to medium plugins
- `FExxx` prefixes map to light plugins
- `FFxxxxxx` prefixes are treated as runtime or temporary handles

The script streams the dump file, so it can process large handle reports without
loading the whole file into memory.

## What you need

You need three things before you run the parser:

1. Python 3.14 or newer
2. A load-order text file copied from LOOT
3. A `DumpPointerHandles_*.txt` file generated by Starfield Engine Fixes

## Get the load-order file from LOOT

Use the load order exactly as LOOT exports it.

1. Open LOOT
2. Click **Copy Load Order**
3. Paste the copied text into a file such as `load_order_full.txt`

That text file is what you pass to `--load-order`.

## Generate the dump file with Starfield Engine Fixes

The dump file must come from the **Dump Pointer Handles** feature in Starfield
Engine Fixes.

In plain English, that feature exports all valid Cell and Reference handles to
Starfield's `Data\SFSE` folder as a `.txt` file. The export also includes the
Pack-In counts and the handle limits, which is exactly what this parser reads.

There are two practical ways to generate the dump:

- Enable `bDumpPointerHandlesOnGameLoadEvent` to write a dump automatically
  after loading a save
- Enable `bDumpPointerHandlesConsoleFunction` to add the `DumpPointerHandles`
  console command, or the short alias `dph`, so you can generate the dump on
  demand

The `Dump Pointer Handles` feature was added in Starfield Engine Fixes v16.3.

After you generate the dump, look in Starfield's `Data\SFSE` folder for the
resulting `DumpPointerHandles_*.txt` file and use that path with `--dump`.

## Run the script

From this project folder, run the parser like this:

```powershell
$parserArgs = @(
  "--dump", "D:\Games\Starfield\Data\SFSE\DumpPointerHandles_2026-05-09_120000.txt"
  "--load-order", ".\load_order_full.txt"
  "--text-out", ".\actual_report.txt"
  "--json-out", ".\actual_report.json"
  "--csv-out", ".\actual_report.csv"
)

python .\starfield_handle_parser.py @parserArgs
```

If you only want the console report, the smallest command is:

```powershell
$dumpPath = "D:\Games\Starfield\Data\SFSE\DumpPointerHandles_2026-05-09_120000.txt"

python .\starfield_handle_parser.py `
  --dump $dumpPath `
  --load-order ".\load_order_full.txt"
```

## Command-line options

- `--dump`: required path to the `DumpPointerHandles_*.txt` file from
  `Data\SFSE`
- `--load-order`: required path to the LOOT load-order text export
- `--json-out`: optional machine-readable JSON report path
- `--csv-out`: optional CSV export path for the full row set
- `--text-out`: optional path for the same human-readable report shown in the
  terminal

## What the report shows

The human-readable report has two main sections:

- **Top contributors by reference handles** shows the biggest plugins sorted by
  reference-handle count
- **Non-zero rows in actual load-order order** shows every plugin with at least
  one attributed handle, in the same order as your LOOT export

The totals at the top include:

- Cell handles used and capacity
- Pack-In cell count
- Reference handles used and capacity
- Pack-In reference count

## Special buckets in the output

The script can emit a few synthetic rows when the dump does not map cleanly to a
normal plugin entry:

- `[runtime/temp]` is used for `FFxxxxxx` runtime or temporary handles
- `[unresolved]` is used when a line cannot be resolved from either the primary
  FormID or a parent Pack-In fallback
- `[unknown ...]` rows appear when a FormID prefix is valid but your LOOT export
  does not contain that slot

## Why the results may differ from the dump's `ModIdx`

This parser intentionally does not treat `ModIdx` as the source of truth.
In real-world Starfield setups, that field often reflects an internal owner,
pack-in context, or runtime detail instead of the plugin that owns the FormID
prefix.

If a handle's primary FormID points to a full, medium, or light plugin, the
script attributes the handle to that plugin. If the primary FormID is blank or
runtime-only, the script can fall back to the parent Pack-In FormID when one is
present.

## Example workflow

1. In LOOT, click **Copy Load Order** and save the result as `load_order_full.txt`
2. In Starfield Engine Fixes, enable the dump option you want
3. Load a save or run `DumpPointerHandles` or `dph` in the console
4. Find the generated `DumpPointerHandles_*.txt` file in `Data\SFSE`
5. Run the parser with `--dump` and `--load-order`
6. Review the terminal output, or open the optional text, JSON, and CSV reports
